# 04 — Interaction Ideas Backlog (M1–M3)

Future-work catalog of NEW user-interaction ideas, grounded in the existing lesson system. Scope is M1–M3
only. Every idea names the script it extends and is flagged `[Now]` (XRI 3.3.1 + Quest controllers/hand-
tracking, no new hardware) or `[HaptX]` (needs the gloves arriving at M3). Reuse-first per `CLAUDE.md`.

## 1. Design principles
- **The new step-type is the extension point, not new managers.** Each idea below is a new
  `Lesson_Step_Kind` value plus a thin notify branch in `Lesson_Sequencer`. The enum serializes as an int in
  `M1_Lesson.asset`/`M2_Lesson.asset` — **append new kinds at the end only**; reordering corrupts existing
  assets.
- **Reuse the two completion pipelines verbatim.** A 3D select routes through `Notify_Marker_Selected`
  (`Component_Marker` → `Marker_Registry`); an ordered action routes through `Notify_Action(string)`
  (`Action_Interactable`/`Startup_Action_Button` → `Action_Button_Registry`). New physical primitives should
  fire one of these two so `Part_Highlighter`, `Startup_State_Controller`, scoring, and `Wrist_HUD` keep
  working untouched.
- **Preserve the guided-vs-practice contract.** Guided gates and appends red error text; practice suppresses
  prompts/highlights (`Part_Highlighter` and `Startup_State_Controller` early-out when `Mode != Guided`) and
  scores. Assessable kinds must set `Include_In_Quiz` AND be added to the `quizTotal` predicate
  (`Lesson_Sequencer.cs:54`) and the `Build_Practice_Steps` filter.
- **World-Space UI only.** Screen-Space Overlay is invisible in the HMD (`02` §0). New prompts/feedback ride
  existing world-space surfaces (`PromptPanel`, `Wrist_HUD`, monitor panels).
- **Keep snap forgiving and feedback non-revealing.** All grab/place ideas inherit the `02` §4 recipe.
  Sensory cues confirm/deny; they must not preview the correct answer in practice.

## 2. New step-type primitives (back almost every idea below; all append-only to `Lesson_Step_Kind`)

### `Place_Component` — direct-grab + snap  `[Now]`
- **Does:** grab a movable object and seat it at a target pose (component into exploded view, workpiece onto
  vise, padlock onto an isolation point).
- **Extends:** the already-written `02` §4 recipe. New `Placeable_Part` mirrors `Component_Marker` but
  carries `XRGrabInteractable` (unused today) + a target-pose transform.
- **Plugs in:** new `Notify_Placement(string markerId)` mirroring `Notify_Marker_Selected`. Reuses
  `Part_Highlighter` for the source-part glow.
- **Keystone:** `XRGrabInteractable` ships in Starter Assets but every current step is a click or watch.

### `Throw_Switch` — directed flip / press / pull  `[Now]` motion · `[HaptX]` detent
- **Does:** flip a toggle, press a latching button, or pull/twist the E-stop — a directed motion to an
  end-stop, not a tap.
- **Extends:** the `Action_Interactable` → `Action_Id` → `Notify_Action` pipeline; only the trigger changes
  (constrained `XRGrabInteractable` hinge or `AxisMovement` with limits; reaching the end offset fires
  `Clicked`). `Marker_State_Toggle` already gives the on/off visual.
- **Plugs in:** unchanged `Notify_Action`.

### `Turn_Knob` — rotate-to-value / handwheel jog  `[Now]`
- **Does:** grab a knob/handwheel and rotate; rotation maps to a continuous value (jog an axis, set feed/
  speed), completing when a target value is crossed.
- **Extends:** `AxisMovement.MoveBy`/`MoveToTarget`/`OffsetFromOrigin` + `Mill_Demo_Controller` indicators.
- **Plugs in:** `Notify_Action` when `OffsetFromOrigin` crosses target.

### `Hold_Position` — sustained dwell  `[Now]` · `[HaptX]` resistance
- **Does:** hold a control in a state for N seconds (twist-and-hold E-stop reset, keep a two-hand enabling
  control engaged, keep hands clear of an interlock zone before a move).
- **Extends:** `Lesson_Sequencer` timing + a dwell coroutine modeled on `Startup_State_Controller.Search_Home`.
- **Plugs in:** new `Hold_Completed` event handled like `Demo_Finished` in `Advance`/`OnDemoFinished`.

> **Two-handed** is a modifier, not a 5th kind: XRI `XRGrabInteractable.selectMode = Multiple` gives
> two-hand grab on `Place_Component`/`Throw_Switch` with no new primitive.
>
> **Builder note:** scenes are generated by `Training_Builder.cs` from ProMill8000 node bounds (it already
> defines `emergency_stop`, `power_on`, `door_unlock`, `guard_door`, `vice` markers). New interactables must
> be added as a builder step so scene regen doesn't drop them.

### Explicitly out of fit
- Any diagnostic / fault-tree / troubleshooting flow (outside the three chosen directions). The M3
  door-closed robot scenario is admitted only as an E-stop reaction-time assessment, not a diagnosis tree.
- "Add another clickable button" — duplicates `Action_Interactable`/`Startup_Action_Button`.
- Pixel-accurate SCORBASE/CNCBase UI — M2 deliberately uses simplified panels.
- A second persistent HUD / overlay scoreboard — violates World-Space-only; duplicates `Wrist_HUD`.

## 4. Smallest first step (prototype this first)
Wire ONE existing M1 labeled part (vise or spindle head) as a `Place_Component` grab-and-snap step using the
`02` §4 recipe and a new `Notify_Placement` mirroring `Notify_Marker_Selected`. It's low-risk (design already
exists), closes the biggest gap (`XRGrabInteractable` unused; every step is a click/watch), is append-only
(one enum value, one notify branch, one part converted), `[Now]` (no HaptX), and is the substrate that
`Throw_Switch`/`Turn_Knob`/M3 LOTO all build on.
